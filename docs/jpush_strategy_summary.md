# 极光推送完整策略总结

## 概述

本文档总结了极光推送在不同场景下的完整处理策略，整合了两个修复方案：
1. **退出登录时的推送处理**（`jpush_logout_fix.md`）
2. **前台推送Toast问题修复**（`jpush_foreground_toast_fix.md`）

## 推送处理矩阵

| 场景 | 定向推送（别名） | 广播推送 | 显示方式 |
|------|----------------|---------|---------|
| **已登录 + 前台** | ✅ 接收 | ✅ 接收 | 静默处理（无Toast） |
| **已登录 + 后台** | ✅ 接收 | ✅ 接收 | 系统通知栏 |
| **未登录 + 前台** | ❌ 不接收 | ✅ 接收 | 静默处理（无Toast） |
| **未登录 + 后台** | ❌ 不接收 | ✅ 接收 | 系统通知栏 |

## 核心原则

### 1. 前台推送：静默处理
- ❌ **不显示Toast**：避免打断用户操作
- ✅ **可更新红点**：通过消息中心提示
- ✅ **可发送事件**：通知其他页面更新

### 2. 后台推送：系统通知
- ✅ **显示在通知栏**：由Android原生处理
- ✅ **可点击打开**：点击进入应用
- ✅ **系统管理**：用户可控制通知权限

### 3. 退出登录：清除别名
- ✅ **删除别名**：不再收到定向推送
- ✅ **保留服务**：仍可接收广播推送
- ❌ **不停止推送**：避免过度清理

### 3. 退出登录处理

**文件：** `lib/network/public/auth_service.dart`

```dart
/// 清除极光推送别名（仅清除定向推送，保留广播推送能力）
void _clearJPushAlias() {
  Future.microtask(() async {
    // ✅ 删除别名：不再收到通过别名发送的定向推送
    // ✅ 保留 RegistrationId：设备ID不变
    // ✅ 保留推送服务：仍可接收广播推送
    bool aliasSuccess = await jpushService.deleteAlias();
    if (aliasSuccess) {
      logger.info('极光推送别名清除成功（保留广播推送能力）');
    }
    
    // ❌ 不调用 stopPush()
  });
}
```

### 4. 登录时处理

**文件：** `lib/network/public/auth_service.dart`

```dart
/// 设置极光推送别名
void _setJPushAlias(LoginModel user) {
  Future.microtask(() async {
    // ✅ 推送服务已在运行，无需 resumePush()
    
    // 设置别名为用户ID
    String alias = user.id.toString();
    bool success = await jpushService.setAlias(alias);
    if (success) {
      logger.info('极光推送别名设置成功: $alias');
    }
  });
}
```

## 推送类型详解

### 1. 定向推送（Alias Push）

**特点：**
- 通过用户别名（User ID）推送
- 精准到达特定用户
- 登录后设置，退出后清除

**应用场景：**
```
✓ "对方在***锁定了手机"
✓ "您的伴侣到达/离开了某地"
✓ 个人账号相关的通知
```

**生命周期：**
```
登录 → 设置别名 → 可接收定向推送
退出 → 删除别名 → 无法接收定向推送
重新登录 → 设置新别名 → 接收新用户的定向推送
```

### 2. 广播推送（Broadcast）

**特点：**
- 向所有设备推送
- 无需别名或RegistrationId
- 不受登录状态影响

**应用场景：**
```
✓ 系统维护公告
✓ 版本更新提示
✓ 全局活动通知
✓ 安全提醒
```

**生命周期：**
```
应用安装 → 初始化推送 → 始终可接收广播
（不受登录/退出影响）
```

### 3. RegistrationId推送

**特点：**
- 通过设备唯一ID推送
- 设备级别，不依赖用户
- 退出登录后保留

**应用场景：**
```
✓ 设备相关的通知
✓ 地理位置相关推送
✓ 设备异常提醒
```

**生命周期：**
```
应用首次启动 → 获取RegistrationId → 始终有效
（除非卸载应用或重装系统）
```

## 常见问题 FAQ

### Q1: 为什么退出登录后还能收到推送？

**A:** 这是设计行为：
- ❌ **定向推送（别名）**：退出后收不到（别名已删除）
- ✅ **广播推送**：退出后仍能收到（系统公告等）
- ✅ **RegistrationId推送**：退出后仍能收到（设备级推送）

**验证方法：**
```
1. 退出登录
2. 发送定向推送（通过别名） → ❌ 收不到
3. 发送广播推送 → ✅ 能收到
```

### Q2: 为什么前台时收不到Toast了？

**A:** 这是优化后的设计：
- 前台推送改为**静默处理**，不显示Toast
- 避免打断用户当前操作
- 后台时仍会显示**系统通知**

**如果需要提示：**
```dart
// 方案1：消息中心红点
MessageCenter.incrementUnreadCount();

// 方案2：应用内事件
EventBus.fire(NewMessageEvent(message));

// ❌ 不推荐：Toast（太打断用户）
```

### Q3: 退出登录后为什么不完全停止推送？

**A:** 保留广播推送有重要意义：
1. **系统公告**：维护通知、安全提醒等
2. **用户召回**：活动通知可引导重新登录
3. **技术优化**：避免频繁启停推送服务

**如果确实需要完全停止：**
```dart
// 用户可以在系统设置中关闭应用通知权限
// 或者应用内提供"通知设置"功能
```

### Q4: 如何测试推送是否正常？

**A:** 按照以下步骤测试：

**测试1：登录状态前台推送**
```
1. 登录应用，保持前台
2. 发送定向推送
3. ✅ 不应显示Toast
4. ✅ 日志显示"接收推送通知 - 用户登录状态: true"
```

**测试2：登录状态后台推送**
```
1. 登录应用，切到后台
2. 发送定向推送
3. ✅ 通知栏显示系统通知
4. ✅ 点击可打开应用
```

**测试3：退出登录后定向推送**
```
1. 退出登录
2. 发送定向推送（通过别名）
3. ✅ 不应收到任何提示
4. ✅ 日志显示"极光推送别名清除成功"
```

**测试4：退出登录后广播推送**
```
1. 退出登录，切到后台
2. 发送广播推送
3. ✅ 通知栏显示系统通知
4. ✅ 日志显示推送服务仍在运行
```

## 总结

### 修复前的问题 ❌

1. 前台收到推送弹Toast，打断用户操作
2. 退出登录后仍能收到定向推送（如"对方锁定手机"）
3. 推送体验不符合用户预期

### 修复后的效果 ✅

1. **前台推送静默处理**，不打断用户
2. **退出登录后清除别名**，不再收到定向推送
3. **保留广播推送能力**，仍可接收系统公告
4. **后台推送显示通知**，用户可点击打开
5. **整体体验更合理**，符合用户预期

### 技术要点

1. **前台 vs 后台**：通过 `isAppInForeground()` 判断
2. **别名 vs 广播**：别名用于定向，广播用于通知
3. **Toast vs 通知栏**：前台静默，后台通知
4. **删除 vs 停止**：删除别名 ≠ 停止推送服务

**修复时间：** 2025-10-24  
**影响范围：** 推送消息的接收和显示  
**风险等级：** 低（优化用户体验，不影响核心功能）
